## D-01. 핵심 뼈대는 능동적 작업 보조 ✅

**결정:** 준비·보조·정리 중 **작업 중 보조**를 기본 뼈대로 하고, 시키는 것만 하는 게 아니라 **먼저 알아채고 돕는** 능동성을 핵심으로 둔다. 조명 등 환경 제어는 뒤로 미룬다.

**작업 흐름 (모두 음성으로 시작):**

| 단계 | 하는 일 |
|---|---|
| 작업 전 · 준비 | "LED 실습 할 거야" → 필요한 물건을 작업 구역에 꺼내 둠, 빠진 것 알림 |
| 작업 중 · 보조 | 말하면 건네줌 + 다음 단계 물건을 먼저 제안 |
| 작업 중 · **수시 정리** | 다 쓴 물건(다음 단계에 안 쓰는 것)을 알아채고 작업 구역에서 치워 둠 — 작업 공간을 계속 비워 줌 *(11/26 추가)* |
| 작업 후 · 마무리 정리 | 전체 정리, 다음 작업을 고려한 최적 배치 (D-02) |

- 수시 정리는 **사람 손이 작업 구역에 없을 때만** 움직인다. 확인 모드에서는 "LED 다 쓰셨으면 치울까요?"로 묻는다.
- 수시 정리를 하려면 작업 중에도 카메라로 계속 지켜봐야 하므로, **인식·음성·계획이 동시에 도는 부하**를 M1에서 꼭 측정한다 (D-05와 연결).

**"능동적"의 정의 (구현 가능한 수준으로)**

| 단계 | 능동 행동 | 어떻게 아나 |
|---|---|---|
| ① 알아채기 | 지금 작업이 몇 단계인지 추정 | 작업 설명서의 단계 순서 + 카메라로 본 물건 사용 상태(전달 칸에서 가져감, 작업 구역에 놓임) |
| ② 먼저 제안 | "다음은 저항 차례예요. 꺼내 둘까요?" | 다음 단계에 필요한 물건이 아직 보관 칸에 있으면 |
| ③ 먼저 알림 | "LED가 보관함에 없어요" / "저항을 안 쓰고 넘어간 것 같아요" | 필요한 물건이 안 보이거나, 단계가 건너뛰어짐 |
| ④ 스스로 복구 | 놓기 실패 → 다시 확인 → 재시도, 안 되면 사람에게 알림 | 행동 후 결과 확인 (interfaces.md 실패 코드) |

- **능동 모드 (11/26 확정: 모드 선택):**

  | 모드 | 동작 | 기본값 |
  |---|---|---|
  | **확인 모드** | 제안 → 사용자 "응" → 실행 | ✅ 기본 |
  | **자동 모드** | 알리고 바로 실행 ("저항 꺼내 둘게요") | 사용자가 말이나 버튼으로 켬 |

  - 두 모드 모두 **Safety Gate는 똑같이 통과**해야 한다. 모드는 "사람에게 묻는가"만 바꾼다.
  - 자동 모드에서도 **보관 칸 → 작업 구역** 이동만 허용하고, 전달 칸(H) 근처처럼 사람 손이 올 수 있는 곳은 확인을 받는다 (안전).

**이유:** 시키는 것만 하는 팔은 흔하다(선행 사례 다수). "작업 상태를 보고 먼저 돕는 것"이 GenAI가 꼭 필요한 이유이자 차별점이다.

## D-02. 정리 최적화 = 사용 기록 + 공간 효율 융합 ✅

**결정:** 정리할 때 물건마다 칸을 정하는 기준을 두 가지 합친다.

| 기준 | 뜻 | 비용에 반영 |
|---|---|---|
| 사용 기록 | 자주 쓰는 것·다음 작업에 쓸 것은 손 가까운 칸 | `사용 빈도(가중) × 칸까지 거리` |
| 공간 효율 | 칸 크기에 맞는 물건을 넣고, 큰 칸을 작은 물건이 낭비하지 않게 | `칸 크기 − 물건 크기` (남는 공간), 안 들어가면 배정 불가 |

- **계산 방식(안):** `비용 = α × 접근 비용 + β × 낭비 공간`을 물건×칸 표로 만들고 **헝가리안 알고리즘**(최소 비용 배정, `scipy.optimize.linear_sum_assignment`)으로 한 번에 배정한다. 안 들어가는 칸은 매우 큰 비용.
- **비교군:** ① 물건마다 고정 자리(`fixed_home`) ② 사용 기록만 ③ 공간 효율만 ④ 융합. 같은 작업 순서로 꺼내는 거리·시간·칸 사용률을 비교.

**이유:** 처음 아이디어(물류 적재 최적화)와 조수 아이디어를 함께 살릴 수 있고, LLM이 아닌 수학적 최적화가 맞는 부분이라 역할 분리가 분명하다.

## D-03. 명령 입력은 처음부터 음성 ✅

**결정:** MVP부터 음성으로 명령한다. 키보드 입력은 **백업**으로 항상 남긴다.

- 로컬 음성 인식(Whisper 계열, OpenVINO)으로 인터넷 없이 처리. 정확한 모델·속도는 M1에서 측정.
- **소음 대책:** 버튼을 누르는 동안만 듣기(push-to-talk)를 기본으로. 상시 대기(호출어)는 확장.
- **응답:** 화면 표시는 필수, 음성 응답(TTS)은 확장.

**이유:** 손이 바쁜 작업 중에 조수에게 말로 시키는 게 시나리오의 핵심이다. 대신 인식 실패로 데모가 멈추지 않게 텍스트 백업을 둔다.

**영향:** M1에 **음성 인식 기술 검증 Issue 추가** 필요 (한국어 인식률, 응답 지연).

## D-05. 두뇌는 Intel 노트북 하나로 시작 ✅

**결정 (11/26):** 음성 인식·물체 인식·소형 언어 모델·로봇 제어를 **모두 Intel 노트북(Core Ultra 5 225H) 한 대**에서 돌리는 것으로 시작한다. Raspberry Pi와 Hailo는 기본 구성에서 뺀다.

**이유**
1. 핵심 병목은 **소형 언어 모델(3~4B)** 이다. Pi 5는 CPU로 약 2~5 tok/s, Hailo-10H를 붙여도 더 빨라지지 않았다 → 명령 하나에 수십 초로는 능동 보조가 성립하지 않는다.
2. 노트북에 이미 NPU·iGPU가 있어 Hailo를 노트북에 붙이는 건 역할이 겹친다.
3. OpenVINO·Geti 모델을 그대로 쓸 수 있는 건 Intel 계열뿐이다. 다른 가속기는 모델 변환을 새로 익혀야 한다.
4. 노트북도 인터넷 없이 현장에서 처리하므로 **Edge AI**다. 산업 현장에서도 설비마다 Intel 칩이 든 산업용 PC가 두뇌 역할을 하는 구조가 흔하다 → 노트북은 그 **산업용 PC 자리**에 해당한다.

**확장 조건 — 아래 중 하나라도 해당하면 "Pi 5 + Hailo-8L(AI HAT+ 13T)"를 '눈'으로 붙이는 계층형으로 확장한다**

| 조건 | 시점 |
|---|---|
| M1 측정에서 노트북이 음성·인식·언어 모델을 **동시에** 돌릴 때 느려짐 | 12/02 GO/NO-GO |
| 강사님이 Pi·Hailo 활용을 평가 요소로 보심 | 강사님 확인 후 |
| 핵심 기능(능동 보조) 완성 후 시간이 남음 | M4 |

- 확장해도 **Hailo-10H는 필요 없다.** 인식만 맡기므로 가장 싼 Hailo-8L로 충분하다.
- 확장에 대비해 인식 모듈은 `Vision.observe() → WorldState` 경계를 지킨다 (interfaces.md). 그러면 인식만 Pi로 옮기면 된다.
- 노트북이 부족하면 **먼저 모델 축소·양자화**를 시도하고, 그래도 부족하면 같은 Intel 스택의 미니 PC·산업용 보드(UP Xtreme ARL 등)로 옮긴다. 코드 수정은 없다.

**강사님께 확인할 질문:** "노트북 하나로 충분하면 노트북으로 가고, Pi + Hailo는 인식 분리용 확장으로 두려는데 괜찮을까요? 아니면 Pi·Hailo 활용이 꼭 들어가야 할까요?"

### 구성 방식

| 구성 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 노트북 하나** | ①에서 전부 | 가장 단순, 추가 비용 0, 배운 스택 그대로 | 장치가 큼 |
| **B. Intel 미니 PC 하나** | ②에서 전부 | 작고 같은 스택, Intel 공식 로봇 두뇌 방향과 일치 | 구매 비용·배송 시간 |
| **C. 계층형** | Pi(+HAT)가 카메라·인식·조명 같은 "현장 손발", 노트북이 음성·LLM·계획 | "현장 장치 + 엣지 서버" 구조로 설명하기 좋음 | 장치 간 통신·변환 작업 추가, 3주 일정에 부담 |

**당시 추천:** **A로 시작**해서 M1~M3를 진행하고, 강사님이 소형·계층 구조를 원하시면 **C를 M4 확장**으로 둔다. 예산이 있으면 B로 옮기는 건 코드 수정 없이 가능(같은 Intel 스택).
